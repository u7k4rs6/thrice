Method of measurement

Four steps
01
Fork snapshot

A cloud sandbox is forked from a snapshot of the app at a pinned version. The release under test is fixed before the run starts.

02
Seed known state

Backend state is written directly over OTLP, so every run begins from facts the checker already holds and can assert against.

03
Three parallel browsers

The reported steps are carried out three times at once, in three separate cloud browsers, from the same seeded state.

04
Check predicates

Concrete predicates are checked against backend state. The verdict comes from those checks, not from a model’s account of what it saw.

ground truth

Every entry is a jaeger-ui issue that has already been fixed, so the correct answer is known from the commit that fixed it. For each issue two releases are pinned: the last release that carried the bug and the first that carried the fix.

A correct instrument reads REPRODUCED on the buggy release and NOT_REPRODUCED on the fixed one. Each release is attempted once, twelve attempts across six issues, and each verdict comes from predicates checked against seeded backend state.

Stated tolerances

Read with the number
Sample size

Five conclusive entries. One verdict moves precision or recall by roughly 0.20, so both figures should be read as a first calibration, not a rate.

Scope

One application, one class of bug report, one set of hand-written predicates. Nothing here shows how the method transfers to another app.

Instrument error

One of the two wrong answers came from the evaluator, not from the app under test. The evaluator is part of what is being measured.

Three runs, unvalidated

63 runs produced zero divergence and no FLAKY verdict. Running three times bought nothing here: the corpus was selected for small deterministic seeds, which is close to selecting for non-flakiness.
